## P1 多指触摸：全局指针数当闸门，第二根手指让整块输入失效

**文件与位置**
- `MiniGameView.java:263` `if(board!=null){if(e.getPointerCount()==1)boardDown(x,y);return true;}`
- `MiniGameView.java:265` `if(e.getPointerCount()>1||pool.moving)return true;`
- `MiniGameView.java:256` 结算按钮同样要求 `e.getPointerCount()==1`
- 对照：`MiniGameView.java:225` 已有 `oneOwner(side)`，`MainActivity.java:619` 已有 `ownerCount(side)`，但棋类和台球完全没走这套归属逻辑（两处在 `owners.put` 之前就 `return`，所以棋类/台球的 `owners` 永远是空的）

**触发条件**
屏幕上同时存在 ≥2 个 pointer。最常见的三条路径：
1. 一方点"准备"后手指没抬起，倒计时结束进入 PLAYING，另一方点棋盘——`getPointerCount()==2`，落子被丢弃。
2. 对方把手或拇指搭在屏幕任意位置（同屏双人很常见），本方的落子、确认、悔棋、台球瞄准全部无响应。
3. 台球：一根手指按住力度条，另一只手想点桌面瞄准——`>1` 直接 return，只能交替操作。

**影响**
- 五子棋/井字棋：无法落子、无法"确认落子"、无法悔棋，玩家只会觉得"点了没反应"，且没有任何提示。
- 台球：无法对准、无法击球。
- 结算页：`再战一局`/`返回大厅` 失效，只能抬起多余手指。
- 与 `docs/开发说明.md`"双方可以同时操作"的承诺相反：这里恰好是"第二根手指让双方都不能操作"。

**修复建议**
把"限制同时操作"从全局指针数改为按归属判断，与相扑一致：
- 棋类不再用 `getPointerCount()` 拒绝输入，改为记录落子者（见 P2），其它 pointer 忽略但不阻塞；
- 台球把 `>1` 改成"选定 `powerPointer`/`aimPointer` 后忽略其它 pointer"，而不是整体 return；
- 结算按钮改为 `owners.size()==0 || 已过冷却`，不要依赖 `getPointerCount()`。

**验证办法**
- 手测：一根手指按住屏幕空白处不放，另一根手指点"确认落子"和"再战一局"，记录是否响应；抬起多余手指后再点，应恢复。
- 手测：点"准备"后保持按住，倒计时结束后让对手点棋盘。
- 自动化：构造双 pointer 的 `MotionEvent`（ACTION_DOWN + ACTION_POINTER_DOWN）喂给 `MiniGameView`，断言落子计数变化。注意这属于视图测试，不等同真机触控。

## P2 五子棋交互：选点与确认没有归属，对方可以替你落子

**文件与位置**
- `MiniGameView.java:230-237` `boardDown(...)`：只在 `phase==PLAYING` 与 `getPointerCount()==1` 下工作，全程不看 `side`
- `MiniGameView.java:233` 确认分支 `if(y>=662&&y<=724){if(candidateX>=0)playBoard(candidateX,candidateY);return;}`
- `MiniGameView.java:235` 选点分支直接写 `candidateX=xx;candidateY=yy;`
- `MiniGameView.java:226-229` `playBoard` → `BoardMatch.java:14` `play()` 用的是 `board.turn`，与"谁点的"无关

**触发条件**
轮到红方，红方已选好点（候选圈已出现）。此时蓝方点"确认落子"，或蓝方先点一个点再点确认。
甚至单人可连续完成：点棋盘 → 点确认 → 点棋盘 → 点确认，替双方各走一步。

**影响**
- "预选后确认"这道防误触的保护等于没有：落哪一子不由当前手决定。
- `docs/v3.0开发记录.md` 写的是"五子棋点选后确认，支持双方同意悔一手"，实际是"任何人可替任何人确认"。
- 配合 P1，一旦屏幕上多一根手指，确认按钮又完全失灵——同一处交互在两种极端间摆动。

**修复建议**
- `boardDown` 记录 `candidateOwner`（选点时的 pointerId 与 side），确认时要求同一 owner；或在确认按钮上直接标注归属（"红方确认"/"蓝方确认"）并按半屏归属校验。
- `turn` 变化时清空 `candidateX/Y`（现在只在 `playBoard`/`undoMove` 里清），避免跨手残留。
- 若要保留"任意一方都能按"的便利，至少在确认前把候选点归属显示出来，避免被误认为作弊。

**验证办法**
- 双人分工手测：A 选点后不动，B 点确认，观察是否落子以及落在谁的点上。
- 单测：直接驱动 `BoardMatch`，断言 `play()` 只认 `turn`；视图层再断言 `candidateOwner` 校验（若采纳修复）。

## P3 暂停恢复：`clearInput()` 清空刹车，弯道中恢复必然打转

**文件与位置**
- `MiniGameView.java:53` `setPaused(value){paused=value;lastFrame=0;accumulator=0;clearInput();...}`
- `MiniGameView.java:54` `clearInput(){...if(race!=null)race.brake[0]=race.brake[1]=false;}`
- `RaceMatch.java:19-21` 目标速度 `brake?190:375`，加速度 `225/s`
- `RaceMatch.java:22` `if(curve(i)&&speed[i]>272&&cooldown[i]<=0){spin[i]=.65;cooldown[i]=1.5;speed[i]=75;...}`
- `MainActivity.java:443-449` `pauseForSettings()` 里 `mini.setPaused(true)`；`MainActivity.java:478` 对话框关闭时 `mini.setPaused(false)`

**触发条件**
弯道中按住刹车（速度已稳定在 190）→ 打开"中场休息"（顶部返回箭头，或系统返回键，`MainActivity.java:119-123`）→ 点"继续对战"。
玩家的手指很可能一直按在屏幕上，但对话框期间事件不进入 View，`brake` 已被置 false，且**没有任何新 DOWN**，所以恢复后仍然是松手状态。

**影响**
- 从 190 加速到 272 只需 `(272-190)/225 ≈ 0.364 s`。也就是说恢复后三分之一秒内必然触发 `spin`，速度被打到 75，再花约 0.65 s 回速——按 `docs/v3.0开发记录.md` 里 17.29 s 的完赛量级，这一下基本决定胜负。
- **正确操作的玩家被惩罚**：什么都没做错，只是被打断。
- 暂停入口是双方共用的（系统返回键就在蓝方那一端），因此暂停本身可当作打断对手的手段，属于公平性问题。

**修复建议**
- `setPaused` 只清 `owners`，不清 `brake`；或暂停时快照 `brake[]`，恢复时还原（还原后若玩家其实已松手，最多多刹一瞬，比强制打转安全）。
- 更稳的做法：恢复时先给 0.4–0.6 s 输入宽限（速度上限钳在 190，或直接冻结物理），并在画面上提示"重新按住刹车"。
- 若产品坚持"暂停即释放所有按键"，则恢复时补一个 3 秒倒数，让双方都有重新按下的机会。

**验证办法**
- 纯逻辑单测（不需要真机）：`RaceMatch` 置 `brake[0]=true`，步进到弧段且速度 190，再把 `brake[0]=false`，按 1/120 步进，断言 `spin[0]>0` 出现在 0.364 s ± 0.02 s。
- 手测：弯中按住刹车 → 暂停 3 秒 → 继续（手指不抬起），观察是否打转；再把手抬起重按，对比结果。

## P4 冰球边界：球门口内侧按"当前 x"判墙，进球被拉回场内

**文件与位置**
- `BallDuel.java:62-65`
  ```java
  if(x<137||x>263){
      if(y<169){y=169;vy=Math.abs(vy);events|=1;}
      if(y>631){y=631;vy=-Math.abs(vy);events|=1;}
  }
  if(y<145)goal(1);else if(y>655)goal(0);
  ```
- 同一段代码被 HOCKEY 与 PINBALL 共用（`BallDuel.java:54-66`）
- 绘制：`MiniGameView.java:154` 球门线 `line(137,158,263,158,RED,7)`；`MiniGameView.java:151` 场地 `rect(27,153,373,637,...)`

**触发条件**
球（半径 9）以斜角射向球门，在 `145 < y < 169`（或 `631 < y < 655`）这条 24 单位的带内，x 漂出 `137..263`。
具体判据：进门时 x 距门柱约 10 单位以内，且横向速度与纵向速度同量级（球速上限 900，1/240 子步位移 3.75，带内约 4–6 个子步，横向可漂 10–20 单位）。

**影响**
- 球已越过画出来的球门线（y=158），却被 `y=169` 一把拉回 19–24 单位并反弹——视觉上是"进了又弹出来"，玩家会判定为判定错误。
- 属于边界逻辑顺序问题：先判墙、后判进球，而墙的适用范围又取决于"当前帧的 x"，不是"穿越方向"。
- 同一处还有第二个边界不一致：`BallDuel.java:42/69` 的左右墙是 `49/351`，而冰球场画在 `27..373`（`MiniGameView.java:151`），球心 49 → 球边 40，离可见挡板约 10 逻辑像素。乒乓的场地线在 `42..358`，球边 40 刚好贴线，说明这对常量是按乒乓调的，冰球/弹球沿用时就成了"隐形墙"。

**修复建议**
- 判定顺序改为"先进球、后挡墙"：`if(inGoalMouth(x) && y<169) → goal`，只在 x 明确在门柱外侧时才反弹。
- 或用穿门判据：仅当"上一帧 x 与当前 x 都在门内"才允许穿过 y=169，避免球从门柱侧面挤出去被弹回。
- 左右墙按模式区分：HOCKEY/PINBALL 用 `38/362`（= 27 + 球半径的近似）或统一由绘制常量反推，避免两套数字。

**验证办法**
- 纯逻辑单测：构造 puck `(140, 170, vx=-200, vy=-300)`，按 1/240 步进，断言是否出现 `x<137 && y<169` 同时 `y` 被改写为 169、且 `winner` 未变——能稳定复现即证实。
- 手测：贴着门柱内侧斜射，观察球是否弹回；沿左右挡板缓慢推球，观察球是否在离挡板约 10 px 处提前反弹。
- 注意：以上为规则/视图层验证，不能代替真机手感。

## P5 台球：`对方球入袋计给对方` 让非击球方直接获胜，且与场内目标文案冲突

**文件与位置**
- `PoolMatch.java:34` `if(inPocket(b)){ ... if(b.owner>=0){score[b.owner]++;events|=2;}else scratch=true; }` —— 球归谁，分就记给谁，不看击球方
- `PoolMatch.java:52-60` `finishTurn()`
  ```java
  if(score[0]==3&&score[1]==3)winner=scratch?1-turn:turn;
  else if(score[1-turn]==3)winner=1-turn;
  else if(score[turn]==3)winner=scratch?1-turn:turn;
  if(scratch)respawn();
  if(scratch||score[turn]==ownBefore)turn=1-turn;
  ```
- 文案：`GameCatalog.java` 中 POOL 的 `goal` 是"每方 3 个本色球，先全部入袋获胜"，`rule` 里才补了"对方球入袋计给对方"
- `MiniGameView.java:221` 结果页 `pool.scratchLoss?"对手清台时白球落袋":"本色三球全部入袋"`

**触发条件**
红方把蓝方的 3 个球全部打进（或打进蓝方第 3 个球）。`score[1-turn]==3` 立即成立。

**影响**
- 蓝方一杆未出手就以 3:0 获胜，红方"越打越输"；`winner` 在 `finishTurn` 里被判给非击球方。
- 结果页对胜方显示"本色三球全部入袋"，实际是输方替他打进的，说明与画面自相矛盾。
- 与 `goal` 文案"先全部入袋获胜"直接冲突：玩家读目标读不出"打对方的球等于送分"。
- 已判胜之后仍执行 `respawn()` 并 `turn=1-turn`，状态不自洽（当前无害，但以后加复盘/续局会踩）。

**修复建议**
两条路，选一条并让文案同步：
- (a) 对方球入袋不计分，只判犯规/换手（更接近玩家直觉，也堵死"被获胜"）；
- (b) 保留记分，但把 `goal` 改成"清空本色 3 球（对方误入也算入袋）"，并禁止非击球方在同一杆内直接获胜（`winner` 只允许是 `turn` 或平局），把"清台白球同落判负"单独处理。
另外把 `respawn()`/`turn` 切换放进"未结束"分支里。

**验证办法**
- 单测：连续打进 `owner==1` 的三个球，断言 `winner` 与结果文案；再测"同一杆打进己方第 3 球 + 白球"确认判负仍生效。
- 手测：实际打三杆把对方球全部打进，看结果页文字与比分是否自洽。

## 二、次要观察（不计入前五，均已核对代码）

1. **准备页任意点击即 ready**：`MiniGameView.java:258-260` 只校验 `y` 在 155..646，没有按钮热区；在自己半场点空白也会显示"已准备，等对手"，可能让对手误判可以开局。
2. **切后台会吞掉暂停面板**：`MainActivity.java:132` 的 `game.reset()` 会顺带 `dismiss()` 共用对话框，触发 `onDismiss` 里的 `mini.setPaused(false)`，随后才被下一句重新置 true；`onResume`（`MainActivity.java:133`）又无条件 `setPaused(false)`。结果是"暂停 → 切后台 → 回来"直接继续对局，面板消失。
3. **台球力度下限偏高**：`PoolMatch.java:23` 初速 `150+power*740`，而滑块最小 5%（`MiniGameView.java:266` clamp `.05`）→ 最低 187，做不到轻碰做球。
4. **倒计时"3"不发声**：`MiniGameView.java:260` 预置 `countSound=3`，`step()` 里只有 `number!=countSound` 才响，所以"3"静默出现，只有 2、1 响。
5. **五子棋确认按钮点击区比视觉大 5 px**：绘制 `662..719`（`MiniGameView.java:145`），判定 `662..724`（`MiniGameView.java:233`）。
6. **赛车提示文字被刹车按钮覆盖**：`drawHeader` 的说明在 `y=135`（`MiniGameView.java:107`），`drawRace` 的红方刹车按钮画在 `113..151`（`MiniGameView.java:193`），后画覆盖先画。

## 三、未证实 / 仅为猜测（不要当结论用）

- **冰球球槌高速划过时"粘球/抖动"**：`collideCircle` 只把球推到接触面并给法向冲量，不带摩擦与切向带动，理论上快速横扫会让球在槌边反复被"推着走"。未复现，未验证。
- **弹球无重力无阻尼**：`BallDuel.java:58-61` 的 PINBALL 分支只有挡板与弹力柱，没有重力、没有衰减，球只会在墙与柱之间长期反弹，理论上存在长时间不进中央失球口的情况。属于设计观察，未跑过。
- **10 px 隐形墙的观感影响**：无法判断在真机上是否明显，需实机对比。

## 四、已检查、未发现阻塞性问题的部分

- **台球碰撞**：子步 `ceil(dt*240)`，`dt=1/120` → `h=1/240`，球速上限 890，单步位移 3.7 < 球直径 20，不存在穿透；冲量等质量、`e≈0.98`、法向由重叠方向给出，方向正确；库边 `60/340/190/610` 与球半径 10 对齐（球边 50 ≈ 台面 49），未发现碰撞级缺陷。
- **台球回合**：进本色球继续、未进/白球落袋换手、清台白球同落判负（`score[turn]==3 && scratch`）三条与 `docs` 描述一致；`ownBefore` 用分数差判断是正确做法。
- **赛车物理对称性**：两车共用 `LENGTH/225/680/272`，无车道长度差（`pose()` 的 `lane` 仅视觉）；平局只在同一子步冲线且差 <1e-8 时成立，真实对局几乎不可能平局，但"完全相同输入"可复现。
- **棋类胜负**：四方向计数、`count>=target`（长连也胜）、满盘平局、`undo()` 把 `turn` 还原给落子方，均正确。
